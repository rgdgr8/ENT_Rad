[unit=HandleRegistration, role=unit]
== <<Unit>> HandleRegistration
This document specifies the design of the unit *HandleRegistration*, it is part of the link:../../main.{type}[metadataservice_conradlib].

This class is responsible to check if a backend registration is required.
Also, it has to save when the last successful registration occurred.

== Provided Interface (public methods and properties)

=== HandleRegistration.timeLastRegistrationRequest

This property saves the timestamp of the last successful registration request in milliseconds as Long.
The variable is nullable and null by default, this means that no registration request was performed ye.

[,kotlin]
----
var timeLastRegistrationRequest: Long? = null
----

=== HandleRegistration.class(tokenHandler: TokenHandler): HandleRegistration

The constructor of this class receives the token handler used to create jobs.

|===
|name|value range |valid values | description

|TokenHandler
|TokenHandler-Instance
|The handler that should be used to generate link:unit_RegistrationRequestJob.adoc[RegistrationRequestJob] instances.

|===

=== HandleRegistration.ensureRegistration()

This instance function uses isCookiePresentAndValid() to check if the registration must be done.
If the cookie is not valid, it should run link:unit_RegistrationRequestJob.adoc[RegistrationRequestJob] synchronously.

*Arguments*

None

*Return*

None

*Exceptions*

* link:unit_RegistrationFailureException.adoc[RegistrationFailureException]: If RegistrationRequestJob failed.

=== HandleRegistration.isCookiePresentAndValid(): Boolean

This static function checks if a registration was successful and a registration cookie is valid.

The function should behave as follows, sorted by priority:

- timeLastRegistrationRequest is null => false
- Session disabled
* timeLastRegistrationRequest is older than maxRegistrationAge => false
* else => true
- Session enabled
* sessionCookieName is null => false
* Session cookie not exist => false
* Session cookie is expired => false
* else => true

*Arguments*

None

*Return*

|===
|Type|value range |valid values  | description

|Response
|Boolean
|true, false
|True if registration and cookie are valid, otherwise false.
|===

*Exceptions*

None

=== HandleRegistration.setRegistrationResult(api: ApiResultObject, requestConfig: ConfigObject)

After successful registration set the received configs by this function.
It should write the parameter values into the Config class.
timeLastRegistrationRequest must be set to now.
If requestConfig contains a connection keepalive value, it should configure the HTTP client by the value.

*Arguments*

|===
|name|value range |valid values | description

|api
|ApiResultObject
|ApiResultObject-Instance
|The api result that should be saved into the global config.

|requestConfig
|ConfigObject
|ConfigObject-Instance
|The config result that should be saved into the global config.
|===

*Return*

None

*Exceptions*

None

[[section-design-decisions]]
== Design Decisions

=== Middleware vs integrate in job

A decision had to be made if we use a middleware or a separate job for the registration check.

==== Option 1: Middleware

A middleware can check in multiple jobs that the registration is up-to-date.

==== Option 2: Integrate in every job

Integrate the relevant mechanism in every job so that they can check individual the current registration and cookie status.

==== Option 3: Integrate in separate job

Use the RegistrationRequestJob and start it before the current job is executed to check the registration and cookie status.

==== Conclusion:

That every job check the status may cause to problems if we have to change something in the conditions.
Also, every job has to know all the conditions how to handle different registration errors. +
If we integrate the check within the RegistrationRequestJob, this job must be initialized for every other job.
This can slow down the request and need more resources for only a short check. +
With the middleware we can quickly check the current registration and cookie status in every job without implement the logic in every job.
And we can start the RegistrationRequestJob only if we need a new registration. In all other cases the current job is running his normal way. +
With all this information we decided to use the middleware to generate a light way check mechanism.
