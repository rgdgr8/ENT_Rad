== <<Unit>> ExecutorWorker
This document specifies the design of the unit *ExecutorWorker*, it is part of the link:../../main.{type}[metadataservice_conradlib].

This class should be a Kotlin object (Singleton) and wrap an instance of link:unit_PausableThreadPoolExecutor.adoc[PausableThreadPoolExecutor].
The PausableThreadPoolExecutor must be initialed with following parameters:

- corePoolSize: 1
- maximumPoolSize: 1
- keepAliveTime: 0L
- unit: No Matter
- blockingQueue: LinkedBlockingQueue.class

== Runtime View

[dynamic_sequence=startup, unit=ExecutorWorker, role=dynamic_sequence]
=== Startup

At startup, it should initialize a new instance of PausableThreadPoolExecutor and save it internally.
The required parameter values are defined in capital 1.

[dynamic_sequence=shutdown, unit=ExecutorWorker, role=dynamic_sequence]
=== Shutdown

Because this is a Kotlin object (Singleton), there is no shutdown for it.
The executor should remain forever so that future requests can be processed easily.
The thread is automatically terminated during app shutdown, nothing needs to be done.

[dynamic_sequence=startup_after_s2r, unit=ExecutorWorker, role=dynamic_sequence]
=== Suspend

Since this is a kotlin class without android references, no suspend state needs to be considered.

== Design Decisions

=== One worker vs multiple worker

A decision had to be made how much worker we should use for the backend requests.

==== Option 1: One worker

Only one worker and a queue for all jobs.

==== Option 2: Multiple worker

Multiple worker with only one queue or a separate queue for every worker.

==== Option 3: Special worker for every job

Special worker with separate queues for dedicated jobs.

==== Conclusion:

On the one hand we want to process the jobs quickly and on the other hand we want to prevent race conditions.
In every multi-worker scenario we have to deal with job synchronization, especially with the registration job, the cookie handling and the server downtime handling. +
For these reasons we decided to use only one worker and create blocking calls like the registration to ensure we use always a correct config from the backend
and have a valid cookie stored.
For all other requests we use the parallel http request worker from OkHttp with separate callbacks to parallelize the backend requests.
