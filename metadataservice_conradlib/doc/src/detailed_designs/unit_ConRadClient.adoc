[unit=ConRadClient, role=unit]
== <<Unit>> ConRadClient
This document specifies the design of the unit *ConRadClient*, it is part of the link:../../main.{type}[metadataservice_conradlib].

The ConRadClient class is the entry point into the library, it must be initialized by the app.

The class should implement a static init counter, so it can log how often this class was initialized by the app.

== Provided Interface (public methods and properties)

=== ConRadClient.class(context: Context, loggerChannelRoot: String?): ConRadClient

The constructor should initialize the Logger and print the version to the IRC,
also it should log the current client version and how often this class was initialized.

*Arguments*

|===
|name|value range |valid values | description

|context
|android.content.Context
|android.content.Context
|Android Context that is used by the link:unit_TokenHandler.adoc[TokenHandler].

|loggerChannelRoot
|String?
|String or null
|The root that should be used by the logger.
|===

Request information about a radio bearer at the backend.

*Arguments*

|name|value range |valid values | description

|bearer

|IBearer-Instance
|The bearer that should be requested at the backend.

|eTags

|callback
|IRadioStationDataCallback
|IRadioStationDataCallback-Instance
|The callback that should receive the information.
|===

*Return*

None

*Exceptions*

None

*Special attributes*

** async: The function should do all networking asynchronously.

[[section-design-decisions]]
== Design Decisions
=== Returning results vs callback
A decision had to be made how to deliver the requested bearer information.

==== Option 1: Return
By returning the information from the calling method, the calling app does not have to implement a callback.

==== Option 2: Callback
The advantage of the callback is that it can be called async and do not block the caller.

==== Conclusion:
As we do not know how long it can take to retrieve the information from the backend, we do not want to block the caller and decided to use a callback to provide the bearer information.

=== Request configurations by our self or receive it from metadataservice
A decision had to be made how we can get the information from the service list like disable reasons or server url or the network information.

==== Option 1: Receive it from metadataservice
Metadataservice have to read the list either way, and so they can send us all relevant information. Also, the need to know the current network status.

==== Option 2: Read the service list by our self
We request and evaluate the service list and network status by our self and decide what to do.

==== Conclusion:
To avoid duplicate code and reduce the work load we decided to receive the relevant information within the service list
and the network status from metadataservice.
