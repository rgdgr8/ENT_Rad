## Why direct `ProgramInfo` is still valuable

Media-browser data is a projection published by the radio application. It may update asynchronously after the hardware tuner changes. The tuner’s `ProgramInfo` is closer to the source of truth because it contains the actual current:

- DAB ensemble
- SID
- frequency
- ECC
- tuned state
- station name

The authoritative flow would therefore be:

```text
Current tuner ProgramInfo
    -> exact bearer/SID/DAB identity
    -> matching media-browser item
    -> RPUID
```

The current flow is:

```text
Media browser/session data
    -> inferred current identity
    -> RPUID
```

If the media browser were guaranteed to update synchronously and expose the exact current tuner identity, direct `ProgramInfo` would not be necessary. The log shows that guarantee does not hold in this environment.

Also, the current repository has no direct tuner callback or IPC contract. That is why the implementation currently relies on media-browser data and why direct tuner integration remains a platform integration task rather than something MetadataService can safely invent locally.

User: then what other option do we have for detecting station change other than polling?

GitHub Copilot: Best alternatives, in order:

1. **`MediaController.Callback`**
   Register a callback on the active radio controller and react to:

   - `onMetadataChanged`
   - `onQueueChanged`
   - `onExtrasChanged`
   - `onPlaybackStateChanged`
   - `onSessionEvent`
   - `onSessionDestroyed`

   When one fires, debounce briefly, then resolve the station identity once. This removes the two-second polling loop while still using the radio app’s exposed media data.

2. **Vendor radio station-change event**
   The radio application could publish a broadcast, binder callback, or service event containing:

   ```text
   bearer
   SID
   ensemble
   frequency
   ECC
   station name
   ```

   This is preferable because it can expose the actual tuner identity directly.

3. **Direct tuner callback**
   Use the platform `RadioTuner`/`ProgramInfo` callback if the privileged-app permissions and tuner service access are available. This is the strongest source, but the current repository has no such integration or permission contract.

4. **Media-browser subscription callback**
   If the radio app exposes station changes through its `MediaBrowserService`, subscribe to children/extras changes and resolve after `notifyChildrenChanged()`.

The practical improvement for this repository is:

```text
MediaController.Callback event
    -> debounce 500-1500 ms
    -> read current media item/extras
    -> compare exact bearer/SID identity
    -> resolve RPUID once
    -> restart Radioplayer subscription only if RPUID changed
```

Keep polling only as a slow fallback, for example every 10–30 seconds when callbacks have not produced a valid station identity. A callback-only solution may miss station changes if the radio app does not publish metadata or queue updates, so the safest design is event-driven detection plus a low-frequency recovery poll.
