== Assumptions
In order to implement this concept, some preconditions needs to be provided:

* CoreServices should implement ServiceListApi including APN configuration and network settings
* ConnectivityManager SystemApi should be usable

== APN1 Configuration
Consumed data by the applications is fully paid by OEM. It is accessible to the app only when it is configured correctly.
Initially, APN1 is configured for the MetadataService.

=== Permissions

MetadataService should have these permissions in its AndroidManifest.xml file:

<uses-permission android:name=**"android.permission.CONNECTIVITY_USE_RESTRICTED_NETWORKS"**/> +
<uses-permission android:name=**"android.permission.INTERNET"**/> +
<uses-permission android:name=**"android.permission.ACCESS_NETWORK_STATE"**/> +
<uses-permission android:name=**"android.permission.CHANGE_NETWORK_STATE"**/> +
<uses-permission android:name=**"android.permission.CONNECTIVITY_INTERNAL"**/> +

eso internally, framework.jar from Perforce is planned to be used by the apps in order to have access to **@SystemApi**:

* to use ConnectivityManager object
* to create request/callback objects and
* to set capabilities to a request (like **NET_CAPABILITY_OEM_PAID** capability)

== APN2 Configuration
Customer pays the charge according to the used data volume.

== Switching Between APN1/APN2
MetadataService app already registers itself to CoreServices for registering itself and getting notifications from ServiceListApi and DisableReasonsApi callbacks.
updateServiceList method has list of ServiceEntry objects including APN information and network connection specific data like url, Https operations etc.

**Apn apn** in ServiceListEntry: APN_VENDOR or APN_CUSTOMER

**APN_VENDOR:** OEM paid (APN1)

**APN_CUSTOMER:** customer paid (APN2)

MetadataService is responsible for:

* evaluating APN status change per registered ServiceId (gracenote_v1 or hybridradiodata_v1)
* providing necessary data to GracenoteService and ConRadClient to access to the internet
    - GracenoteService needs APN enum per request
    - ConRadClient needs configData after every APN status change
* creating network interfaces for APN1/2 for the usage of its back-ends

**configData: ** APN enum, url ..etc to switch between different network configurations dynamically

GracenoteService and ConRadClient are responsible for:

* creating their network requests
* fetching the responses

== Risks
These risks can be addressed in the future based on this concept design:

* Emulator does not support to work with socket implementation, so real hardware should be used and this can cause delays during implementation phases
* CoreServices and ConRadClient components plan to work on related features in PI11, this can cause delays for MetadataService implementation during PI10
* A PoC is not done for ConnectivityManager implementation, so some problems during the usage of this API and network interface creation can cause changes on this concept and delays on the real implementation
